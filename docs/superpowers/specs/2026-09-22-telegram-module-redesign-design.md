# Telegram-модуль: автоподключение, живость аккаунтов, SaaS-интерфейс

Дата: 2026-09-22

## Проблема

Подключить канал под мониторинг сейчас — ручная многошаговая работа. Канал
привязывается к аккаунту только явно (форма «привязать аккаунт к цели») или
через «умное добавление», которое ищет канал среди диалогов, где аккаунт
**уже состоит**. Входа в канал в системе нет: если ни один аккаунт не
подписан, «умное добавление» всё равно выбирает аккаунт по нагрузке — и тот
не может читать канал, в котором его нет. Таргет зависает в
`needs_account`.

Живость аккаунта (`fetch_account_session_info`) проверяется только по
нажатию кнопки. Ничего не следит фоном; мёртвый аккаунт обнаруживается по
накопившимся ошибкам заданий, его каналы стоят, пока человек не заметит.

Все активные аккаунты участвуют в распределении нагрузки. Нельзя завести
аккаунт для приватного канала так, чтобы система не раздала ему чужие
каналы.

Страница `/telegram` — один файл на 1798 строк, девять карточек стопкой
(подключить аккаунт, добавить вручную, привязать, сервисные действия, умное
добавление, список, аккаунты, задачи). Список каналов — седьмая карточка
сверху.

Что работает хорошо и сохраняется: range/full-бэкфилл с постраничным
прогрессом (`full_progress` per account), gapfill-опрос при включённом live,
живой листенер на событиях Telethon, сбор комментариев с рекурсивным
обходом, синхронизация участников, скоринг нагрузки аккаунта
(`compute_account_load_score`), лимиты в час и cooldown.

## Решения, принятые с владельцем

- Объём: Telegram-модуль первым, но с выделенной дизайн-системой; остальные
  страницы переводятся на неё следующим заходом.
- Аккаунты пула **вступают** в каналы: realtime через события Telethon
  работает только для каналов, где аккаунт состоит; приглашения `t.me/+…`
  без вступления не читаются вовсе.
- Мёртвый аккаунт пула → его каналы **автоматически** передаются другому
  аккаунту пула. Мёртвый приватный аккаунт → только пометка.

## Решение

### 1. Модель данных

**`ParserAccount`**, новые колонки:

| Колонка | Тип | Назначение |
|---|---|---|
| `pool_mode` | `String(16)`, default `"shared"` | `shared` — участвует в авто-выборе и failover; `dedicated` — только ручное назначение |
| `alive` | `Boolean`, nullable | результат последней проверки; `NULL` — не проверялся |
| `last_checked_at` | `DateTime(tz)`, nullable | |
| `last_alive_at` | `DateTime(tz)`, nullable | |
| `dead_reason` | `Text`, nullable | текст ошибки Telethon при последней неуспешной проверке |
| `join_window_start` | `DateTime(tz)`, nullable | начало суточного окна вступлений |
| `join_window_count` | `Integer`, default 0 | вступлений в текущем окне |
| `last_join_at` | `DateTime(tz)`, nullable | для минимального интервала между вступлениями |

**`Target`**, новые колонки:

| Колонка | Тип | Назначение |
|---|---|---|
| `onboarding_step` | `String(32)`, default `"idle"` | `idle` · `queued` · `resolving` · `joining` · `joined` · `failed` |
| `onboarding_error` | `Text`, nullable | человекочитаемая причина `failed` |

Существующий `onboarding_status` (`ready / needs_account / blocked`, enum в
БД) не трогается: он отвечает «есть ли рабочий аккаунт», новые колонки — «на
каком шаге подключение». Строковые колонки не требуют `ALTER TYPE`.

**Один активный аккаунт на Telegram-канал.** `TargetAccountLink` сегодня
допускает несколько активных связей; `generate_jobs` параллелит
full-бэкфилл по ним. Новое правило: для `parser_type = telegram` активная
связь ровно одна. Обеспечивается частичным уникальным индексом:

```sql
CREATE UNIQUE INDEX uq_tal_one_active_telegram
  ON target_account_links (target_id) WHERE is_active;
```

Индекс ставится в миграции **после** дедупликации существующих связей:
оставляется связь с наибольшим `health_score` аккаунта, остальные
`is_active = false`. Теряется параллельный бэкфилл с нескольких аккаунтов —
надёжность вместо него даёт failover (§3). Darknet-связи под индекс тоже
попадают; у darknet сегодня одна связь на таргет — правило безвредно.

### 2. Автоподключение канала

Один инпут принимает: `@username`, `username`, `t.me/username`,
`https://t.me/username`, числовой id (`-100…` или без префикса),
`t.me/+hash`, `t.me/joinchat/hash`.

Сервис `app/services/telegram_onboarding.py`:

```
onboard(session, *, raw_input, owner_user_id, account_id=None, allow_join=True) -> Target
```

1. **Нормализация.** Расширить `normalize_telegram_identifier`: приглашения
   (`+hash`, `joinchat/hash`) распознаются и хранятся как `invite:<hash>` до
   вступления — реальный id канала известен только после
   `ImportChatInviteRequest`. После вступления `Target.identifier`
   заменяется на канонический (`@username` или `-100…`), исходное
   приглашение сохраняется в `config["invite_hash"]`.
2. **Создание таргета** сразу, в HTTP-запросе: `onboarding_step = queued`,
   `onboarding_status = needs_account`, конфиг из
   `_telegram_target_config` с дефолтами §4. Интерфейс видит строку
   немедленно.
3. **Задание онбординга** ставится в очередь `telegram_backfill`
   (`job_key = f"onboard:{target.id}"`), а не выполняется в запросе:
   вступление может ждать паузу темпа минуты.

Задание (`WhatsApp`-подобный `run` в `TelegramPlugin` по `payload.kind ==
"onboard"`):

4. **Выбор аккаунта.** Если `account_id` задан (ручное назначение с
   dedicated-аккаунта) — он. Иначе кандидаты: `pool_mode = shared`,
   `is_active`, `alive is not False`, доступен по `_is_account_available`.
   Порядок: **сначала те, кто уже состоит в канале** (по `dialogs_cache`,
   `find_dialog_match`) — им вступать не нужно; затем по
   `compute_account_load_score`. Нет кандидатов → `onboarding_step =
   failed`, `onboarding_error = "нет доступных аккаунтов пула"`,
   `onboarding_status = needs_account`.
5. **Вступление** (`onboarding_step = joining`), только если аккаунт не
   состоит и `allow_join`:
   - публичный: `client.get_entity(identifier)` →
     `JoinChannelRequest(entity)`;
   - приглашение: `CheckChatInviteRequest(hash)` для предпросмотра →
     `ImportChatInviteRequest(hash)`;
   - **темп:** не чаще `telegram_join_min_gap_seconds` (900) на аккаунт и
     не больше `telegram_join_daily_limit` (10) за суточное окно. Если темп
     не позволяет — задание переносится (`run_after`), аккаунт остаётся
     выбранным;
   - `FloodWaitError(n)` → `cooldown_until = now + n`, кандидат меняется на
     следующего, задание переносится;
   - `ChannelsTooMuchError` → аккаунт помечается `config["channels_full"]
     = true`, исключается из выбора, следующий кандидат;
   - `UserAlreadyParticipantError` → не ошибка, идём дальше;
   - `InviteHashExpiredError`, `InviteHashInvalidError`,
     `ChannelPrivateError`, `UsernameNotOccupiedError` → `failed` с текстом
     ошибки, аккаунт не наказывается.
6. **Связь и расписание.** `TargetAccountLink(is_active=True,
   auto_detected=True)`; прежние активные связи таргета гасятся (индекс §1
   иначе не пустит). `onboarding_step = joined`, `onboarding_status =
   ready`. Первый бэкфилл — с задержкой `random(120, 300)` секунд через
   `run_after`: свежевступивший аккаунт, мгновенно выкачивающий историю,
   выглядит как бот. Далее — обычный `generate_jobs`.

Существующие формы «добавить вручную», «привязать аккаунт», «умное
добавление кількох цілей» становятся тонкими обёртками над `onboard()`:
массовый ввод — цикл по строкам.

### 3. Живость аккаунтов и failover

**Проверка** — новый шаг в `schedule_once`, гейт по интервалу через
`ServiceState` (ключ `telegram_liveness_last_run`), период
`telegram_liveness_interval_seconds` (600). Для каждого активного
Telegram-аккаунта: `fetch_account_session_info(credentials)` (уже есть:
`is_user_authorized` + `get_me`) → `alive`, `last_checked_at`,
`last_alive_at`, `dead_reason`. Проверка — одно подключение Telethon на
аккаунт; при четырёх аккаунтах дёшево. `# ponytail: последовательная
проверка в планировщике, вынести в отдельный процесс при десятках
аккаунтов`.

Мёртвым считается аккаунт, у которого **две проверки подряд** дали `alive
= False` (одиночный сетевой сбой не должен запускать миграцию каналов).
Счётчик — `config["liveness_failures"]` в credentials.

**Failover:**
- `pool_mode = shared` мёртв → все его активные связи `is_active = false`;
  каждый затронутый таргет получает `onboarding_step = queued` и задание
  `onboard` без `account_id` — его подхватит другой аккаунт пула по §2.
  Мёртвый аккаунт не деактивируется (`is_active` остаётся) — он может
  ожить после повторного входа; `alive = False` уже исключает его из
  выбора.
- `pool_mode = dedicated` мёртв → связи гасятся, таргеты в
  `needs_account`, `onboarding_step = idle`. Ничего не передаётся.
- Аккаунт ожил (`alive = True` после `False`) → ничего не возвращается
  автоматически; его прежние каналы уже у других. Ручное «переназначить» в
  интерфейсе.

### 4. Аккуратный парсинг

Механика сохраняется. Меняются дефолты и одна пауза:

- Автоподключённый канал: `live_enabled = true`, `backfill.enabled =
  true`, `backfill.mode = full`, `backfill_limit = 200`,
  `poll_interval_seconds = 300`, `comments_enabled = true`,
  `participants_sync_enabled = true`. Range-даты не задаются — пользователь
  их не вводил.
- Пауза 2–5 минут между вступлением и первым бэкфиллом (§2 п. 6).
- Листенер уже перечитывает связи по таймеру (`_refresh_seconds`) —
  realtime для нового канала включается без правок.

Один аккаунт на канал (§1) означает, что full-бэкфилл идёт с одного
аккаунта; `full_progress` по-прежнему хранится per account, при
переназначении бэкфилл продолжается с `next_offset_id` предыдущего
аккаунта, если тот есть в `full_progress` — иначе с начала.

### 5. Приватные аккаунты

`pool_mode = dedicated`:
- исключён из кандидатов §2 п. 4 и из доноров failover §3;
- в карточке аккаунта — инпут «Назначить канал»: тот же `onboard()` с
  `account_id` и флагом `allow_join` из чекбокса «вступить, если не
  состою» (по умолчанию выключен — для приватных каналов аккаунт обычно уже
  внутри);
- переключение `shared ↔ dedicated` тумблером; при переводе в `dedicated`
  текущие каналы остаются за аккаунтом; при переводе в `shared` — тоже,
  просто аккаунт начинает получать новые.

### 6. Интерфейс

Визуал — через `/design` (ui-ux-pro-max): светлые минималистичные токены,
оболочка страницы, компонент `Tooltip`, примитивы строки/списка.
Единственная новая зависимость — `@radix-ui/react-tooltip` (остальные
Radix-примитивы, lucide и Tailwind 4 уже в проекте).

**`/telegram`** — верх: один инпут «Ссылка, @канал или ID» + кнопка
«Подключить». Ниже список, строка = объект:

| Колонка | Содержимое |
|---|---|
| тип | иконка: канал / группа / личный чат |
| объект | название; под ним идентификатор серым |
| аккаунт | чип с именем, точка живости (зелёная/красная/серая) |
| статус | мониторится · вступает · ждёт аккаунт · пауза · ошибка (с текстом в подсказке) |
| активность | «5 мин назад», счётчик событий |
| действия | иконки с подсказками: пауза/возобновить · бэкфилл сейчас · переназначить · настройки · удалить |

Строка в `queued/resolving/joining` показывает прогресс; в `failed` —
ошибку и кнопку «повторить».

**`/telegram/settings`** — вкладка «Аккаунты», строка = аккаунт: имя или
телефон · тумблер пул/приватный · точка живости и «проверен 3 мин назад» ·
нагрузка: N каналов, вступлений сегодня K/10 · иконки: проверить сейчас ·
открыть · отключить · удалить. Вкладка «Задачи» — существующая карточка
активных/проблемных задач.

**Подключение аккаунта** — диалог с двумя вкладками:

- **QR-код** (по умолчанию). Поля `api_id`, `api_hash`, метка → кнопка
  «Показать QR». Сервер запускает `client.qr_login()` и отдаёт ссылку
  `tg://login?token=…` уже отрисованной в SVG (`segno`, чистый Python —
  единственная новая зависимость бэкенда). Пользователь сканирует из
  Telegram → Настройки → Устройства. Токен живёт ~30 с — сервер пересоздаёт
  его (`recreate()`) и обновляет картинку, интерфейс опрашивает статус раз в
  2 с и показывает обратный отсчёт. Если у аккаунта включён облачный пароль,
  после скана Telethon бросает `SessionPasswordNeededError` → статус
  `password_needed`, в диалоге появляется поле пароля. Успех → аккаунт
  создаётся с теми же `credentials`, что и при входе по коду.
- **Номер телефона** — существующий флоу (`start-auth` → `complete-auth`)
  без изменений логики, оформленный шагами: данные → код → пароль при
  необходимости.

`api_id`/`api_hash` запоминаются в `localStorage` браузера после первого
успешного подключения и подставляются в обе вкладки — они принадлежат
приложению, а не аккаунту, и одинаковы для всех номеров.

**Где живёт QR-сессия.** Клиент Telethon обязан *ждать* сканирования, а
`ParseJob.target_id` — `NOT NULL`: у входа нет таргета, задание воркера не
подходит. QR-сессии держатся в памяти процесса API (реестр по случайному
токену, фоновая asyncio-задача на сессию, TTL 180 с). Аккаунт создаётся
только при успехе — «висящих» строк не остаётся. Потолок: один процесс
uvicorn (как сейчас в compose); при нескольких воркерах реестр придётся
выносить — `# ponytail:` в коде. Перезапуск API обрывает незавершённые
QR-сессии; пользователь просто начинает заново.

**`/telegram/accounts/:id`** — карточка: статус, нагрузка, ошибка если
есть; список его каналов тем же компонентом строки; для `dedicated` —
инпут «Назначить канал» с чекбоксом вступления.

Девять карточек текущей страницы уходят. «Сервисные действия» (синк
участников, обновить диалоги) — в меню «···» на вкладке «Аккаунты».

### 7. API

Новые эндпоинты (все под существующей проверкой владельца/админа):

| Метод и путь | Назначение |
|---|---|
| `POST /telegram/onboard` | `{input, account_id?, allow_join?}` → таргет со `onboarding_step = queued` |
| `GET /telegram/accounts` | список с живостью, `pool_mode`, нагрузкой (каналов, вступлений в окне) |
| `POST /telegram/accounts/{id}/check` | немедленная проверка живости, возвращает результат |
| `PATCH /telegram/accounts/{id}` | `{pool_mode}` |
| `GET /telegram/accounts/{id}/targets` | каналы аккаунта в формате строки списка |
| `POST /telegram/targets/{id}/reassign` | `{account_id?}` — снять связь, поставить `onboard` (с явным аккаунтом или из пула) |
| `POST /telegram/targets/{id}/retry-onboarding` | из `failed` обратно в `queued` |

`GET /telegram/targets-overview` расширяется полями `account {id, label,
alive}`, `onboarding_step`, `onboarding_error`, `kind` (channel / group /
private) — фронт читает список одним запросом. `kind` берётся из
`dialogs_cache` при онбординге и хранится в `config["kind"]`.

### 8. Ошибки и наблюдаемость

Все переходы `onboarding_step` и результаты проверок живости пишутся в лог
уровня `info`; отказ вступления и смерть аккаунта — `warning` с
`account_id`, `target_id`, классом ошибки Telethon. Никаких внешних
уведомлений — только индикация в интерфейсе.

### 9. Чего не делаем

- Уведомления (почта, бот) о смерти аккаунта.
- Автоматический возврат каналов ожившему аккаунту.
- Редизайн других страниц — следующим заходом на этой дизайн-системе.
- Изменение флоу входа аккаунта по коду / `api_id` / `api_hash`.
- Перевод `onboarding_status` из enum в строку.

## Порядок работ

1. **Данные и сервис** — миграция (колонки §1, дедупликация связей,
   частичный индекс), `telegram_onboarding.py`, обработка `onboard` в
   `TelegramPlugin.run`, нормализация приглашений. Тесты: нормализация всех
   форм ввода; выбор аккаунта с предпочтением состоящих; темп вступлений;
   каждая ветка ошибок Telethon на заглушке клиента; индекс не пускает
   вторую активную связь.
2. **Живость и failover** — шаг в `schedule_once`, правило двух неудач,
   миграция каналов. Тесты: одна неудача не мигрирует, две — мигрируют;
   dedicated не мигрирует; ожившему ничего не возвращается.
3. **API** — эндпоинты §7, расширение `targets-overview`, обёртки старых
   форм над `onboard()`.
4. **Дизайн-система** — через `/design`: токены, оболочка, `Tooltip`,
   строка списка.
5. **Страницы** — `/telegram`, `/telegram/settings`, `/telegram/accounts/:id`
   на новых компонентах; удаление девяти карточек.

Этапы 1–3 — бэкенд, 4–5 — фронтенд; 4 не зависит от 1–3 и может идти
параллельно.

## Проверка вживую

Автотестами вступление в реальный канал не покрыть. Ручной чек-лист перед
merge: подключить публичный канал по `@username` (аккаунт не состоит) →
строка проходит `queued → joining → joined`, через 2–5 минут появляются
события; подключить `t.me/+hash`; остановить сессию аккаунта (разлогинить с
телефона) → через две проверки его каналы у другого аккаунта; тот же
сценарий с `dedicated` → каналы в «ждёт аккаунт».
